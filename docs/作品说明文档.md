## 第 1 章 项目概述

### 1.1 项目背景

大学生求职长期面临"信息不对称"：招聘信息是"岗位语言"，里面混着专业要求、证书、素质、经验等十几个方面，学生很难把它拆解成"我该补什么"；与此同时，学生对自己"强在哪、弱在哪"往往只有模糊感觉，只能凭感觉海投。

现有招聘平台多为"企业发岗位—学生投简历"的流量型产品：功能臃肿、广告与招聘中介信息混杂、匹配结果是黑盒（只给一个匹配度数字，不告诉依据），且几乎没有针对在校生的成长规划能力。面向大学生的轻量化、可解释的求职匹配工具仍然稀缺。

**职引星途** 正是在这一背景下立项：把"招聘信息"和"个人经历"放进同一套十维能力框架里量化对比，让匹配结果可解释、可追溯，并把结论沉淀为一条可执行的成长路线。

### 1.2 项目目标

本项目要实现的是一条完整链路：

```
岗位要什么（岗位能力画像） → 我有什么（学生能力画像） → 差在哪里（人岗匹配） → 接下来怎么补（生涯发展报告）
```

围绕这条主线，实现以下功能目标：

1. **岗位能力画像**：把招聘原文自动拆解为十个维度的要求强度，并抽取具体技能与证书清单（区分"必须/优先"）。
2. **学生能力画像**：以结构化表单采集学生技能、证书、项目与实习经历，生成十维能力得分与可视化星球图。
3. **人岗智能匹配**：用同一套十维基准逐项比对，输出综合匹配度、四大类目得分、十维达成度、技能/证书缺口与提升建议。
4. **个性化生涯发展报告**：生成职业目标、晋升路径、分阶段（1~3 个月 / 4~12 个月 / 1 年以上）成长计划与复盘节点。
5. **求职资源支撑**：校招岗位浏览检索、就业政策与校招资源离线库、知识库与 AI 助手问答。

> 说明：本文档按实际实现描述。大纲中提到的"简历文件上传解析""企业自助发布岗位""TF-IDF 匹配""Redis 热点岗位缓存"不在当前版本范围内，原因见 7.2 节"待迭代方向"。

### 1.3 应用场景

| 高校应届毕业生 / 在校生 | 填报能力画像 → 查看人岗匹配 → 按报告规划大三至毕业的成长任务 |

## 第 3 章 系统设计

### 3.1 总体架构

采用 **B/S 架构**：微信小程序客户端（uni-app 编译产出）通过 HTTPS 调用 Django REST API；AI 相关重任务进入 Celery 任务队列由后台 Worker 调用大模型；PostgreSQL 存储业务数据；Redis 作为 Celery Broker/结果后端。

【图 3-1 系统总体架构图】

架构分层：

```
┌─────────────────────────────┐
│ 微信小程序（uni-app / Vue3+TS）│
│ 页面层 · 状态层(Pinia) · API层 │
└──────────────┬──────────────┘
               │ HTTPS + JWT
┌──────────────▼──────────────┐
│ Django + DRF（REST API 层）   │
│ 用户/画像/招聘/知识库/AI 接口   │
└──────┬───────────────┬──────┘
       │ ORM           │ 任务投递
┌──────▼──────┐  ┌─────▼──────────────┐
│ PostgreSQL  │  │ Celery Worker + Redis│
│ 业务数据     │  │ 调用 DeepSeek 大模型  │
└─────────────┘  └────────────────────┘
```

### 3.4 核心业务流程

**流程一：人岗匹配（学生视角）**

【图 3-3 人岗匹配流程图】

1. 学生填写/更新能力画像（或使用示例数据体验）；
2. 选择目标岗位（校招真实岗位或内置示例岗位）；
3. 前端调用匹配引擎（十维逐项比对，纯函数计算，无网络依赖）；
4. 输出匹配度、类目得分、十维差距、缺口与建议；
5. 系统对"可评估维度过少"或"核心技能不足"的情况自动封顶并给出说明。

**流程二：AI 画像解析（异步任务）**

【图 3-4 AI 任务时序图】

1. 前端提交画像表单 → 后端创建 Celery 任务并即时返回任务号；
2. Worker 调用 DeepSeek 模型，返回结构化 JSON（十维 + 技能/证书 + 置信度）；
3. 前端轮询任务结果接口，成功后渲染画像；超时或失败时降级为本地规则解析；
4. 结果落库（学生画像/岗位画像），供匹配与报告复用。

## 第 4 章 核心技术难点与实现

> 本章只写真正踩过的坑和真实实现，便于答辩现场展开。

### 4.1 十维能力加权匹配引擎

这是项目最核心、也最"不一样"的模块，实现为**无网络、无 UI 依赖的纯函数**（`utils/jobMatch.ts`），可独立单元测试。

**（1）单维达成度与"超出不加分"**

```
岗位要求 <= 55 分      → 视为「无硬性要求」，不参与打分
否则                   → fit = clamp(学生分 / 岗位要求分, 0, 1)
```

"超出要求"封顶为 1：匹配衡量的是"够不够用"，不是"越强越好"。

**（2）置信度加权，把"没写清"的维度自动降权**

有效权重 = 基准权重 × 岗位侧解析置信度 × 学生侧解析置信度。
岗位没写清、学生没填的维度会自动降权，避免用不确定的数据给出确定的高分。

**（3）专业技能/证书用"覆盖率"而不是"比大小"**

两个学生专业技能都是 92 分，但一个学 Java、一个学新媒体，对同一个 Java 岗位，后者覆盖率可以为 0。因此专业技能与证书按"岗位要求条目被覆盖的比例"衡量，并区分"必须（2 倍权重）/优先"。

**（4）三道防误导闸门（本项目独创，答辩重点）**

- 岗位未提要求的维度**不参与加权**：否则"要求写得越少的岗位越容易被匹配上"；
- **核心技能门槛**：专业技能覆盖率为 0 时，总评封顶（30 + 70×覆盖率），避免"其他项满分就把核心技能缺失的岗位判为基本匹配"；
- **信息不足封顶**：当可评估维度少于 3 项时，匹配度按信息完整度封顶并明确提示。真实案例：某岗位原文几乎没写要求，AI 只解析出 1 项要求（专业技能 60 分），学生 88 分满足它，旧版会显示 **100%**，现已修正为 37% 并提示"岗位要求信息不足，仅供参考"。

> 答辩可讲这条：这不是算法调参，而是**对"匹配度会误导人"这一真实缺陷的工程修复**，体现产品思维。

### 4.2 AI 画像解析的异步任务链路

大模型调用耗时且不稳定，不能阻塞 HTTP 请求。实现方式：

- 前端提交 → 后端创建 Celery 任务，**立即返回任务号**（202）；
- Worker 调用 DeepSeek（OpenAI 兼容接口，`response_format=json_object` 约束 JSON 输出）；
- 前端按固定间隔轮询 `task/{id}` / `result/{id}`，成功后渲染；
- 失败或超时 → 降级为本地规则解析（结果标注为"规则解析"，不冒充模型输出）。

**难点与处理**：

- 模型输出 JSON 结构不稳定 → 提示词约束 + 服务端校验与容错解析；
- 任务状态与用户隔离 → 任务带用户归属，查询时校验，防止越权查看他人任务；
- Windows 环境 Celery 无 prefork → 使用 `--pool=solo` 运行 Worker（部署文档已记录）。

### 4.3 权限隔离与数据安全

- 认证：JWT（自定义 `Authorization: JWT <token>` 前缀，与第三方库默认 Bearer 不同，属于踩坑点）；
- 授权：每个资源接口校验"资源归属当前用户"（知识库、文章、画像、收藏），否则返回 403/404；
- 管理：后台管理使用 Django Admin，独立于小程序端；
- 敏感字段：招聘数据中的身份证号、手机号等列在序列化层过滤，不向前端下发；
- 日志：敏感信息（API Key、密码）不落日志。

### 4.4 小程序端的富文本渲染与原生组件兼容性

小程序端有几类"框架级"限制，处理不当会直接白屏或报错，属于真实工程难点：

1. **AI 回答富文本**：三方 Markdown 库在小程序构建后不可用，改为**自研零依赖 Markdown→HTML 渲染器**（标题、列表、代码块、粗斜体、表格），通过 `<rich-text>` 渲染，带 XSS 转义；
2. **编辑器上下文**：`<editor>` 原生组件返回的 EditorContext 不可序列化，存入 `ref` 会触发"对象无法克隆"错误，改为普通变量持有；
3. **胶囊按钮**：自定义导航栏需读取微信胶囊位置，开发者工具中该 API 会报框架错误，需按环境降级；
4. **状态缓存**：知识库列表、折叠状态、选中知识库等状态做本地持久化，避免页面往返丢失。

### 4.5 校招数据同步与幂等设计

- 数据来源：学校就业服务平台导出的招聘信息；
- 幂等：以"企业信用代码 + 岗位名称"等复合键判定，重复同步不产生脏数据（实测 449 条原始数据 → 342 条唯一记录）；
- 增量：支持只同步新增/变更行，避免全量替换；
- 一致性：同步脚本与后台任务共用同一解析与校验逻辑。

### 4.6 隐私与合规

- 政策资源库**不转载原文**、不摘录未经核对的条款数字，只提供来源 + 定位 + 官方链接；
- 画像解析与 AI 问答**不收集身份证号等敏感字段**；
- 声明画像、匹配、报告均为参考工具，不构成录用承诺。

## 第 6 章 创新点与应用价值

### 6.1 创新点（三条）

**① 可解释的十维匹配引擎 + 三道防误导闸门**
不是黑盒打分：每个维度的达成度、依据、缺口都可见；通过"未提要求不参与加权 / 核心技能门槛 / 信息不足封顶"三道闸门，从算法层面杜绝"要求越少越容易匹配""只满足一项就 100%"的误导。这是区别于常见"匹配度数字"产品的核心差异。

**② 离线可用的政策资源库，只给来源与官方链接**
将就业政策、校招渠道、求职指导整理为结构化离线数据，标注来源类型、发布机构与文号，一键复制官方链接；不转载原文、不摘录未经核对的条款数字，规避政策时效与版权风险，也适配网络不稳定的场景。

**③ 小程序端零依赖富文本渲染与异步 AI 链路**
针对小程序环境的组件限制，自研零依赖 Markdown 渲染器 + 原生组件适配，让 AI 回答在真机可用；AI 解析采用异步任务队列，前端轮询，保证页面不阻塞。

### 6.2 应用价值

- **落地场景**：可直接部署到高校就业中心（如聊城大学就业中心）或学院层面，作为毕业生求职辅导的数字化工具；
- **低成本**：微信小程序免安装、无需账号体系迁移，学生打开即用；
- **可复用**：匹配引擎与画像体系与具体岗位数据解耦，更换数据源（不同学校、不同行业）即可迁移；
- **合规友好**：资源库与 AI 使用均有清晰边界，规避版权与政策时效风险。

## 第 7 章 总结与展望

### 7.1 开发总结

本项目完整实现了"岗位画像—学生画像—人岗匹配—生涯报告"的主链路，并在真实联调中解决了鉴权、异步任务、原生组件兼容、匹配误导等一系列工程问题。最大的收获是认识到：**求职类产品最容易犯的错误是"给出一个漂亮的数字"**，而本项目的价值恰恰在于把每个数字的依据、边界与不确定性都摆到用户面前。

### 7.2 待迭代方向

1. **简历文件解析**：支持 PDF/Word 简历上传，自动抽取技能与经历（当前以结构化表单替代，降低小程序填写门槛）；
2. **企业端扩展**：企业自助发布岗位与校招活动，配套审核与统计后台；
3. **消息通知**：投递状态、匹配结果更新等站内消息；
4. **真机与并发验证**：正式环境多机型、多并发压测；
5. **大模型简历润色、视频面试预约**等求职辅助能力。

## 第 8 章 AI 工具使用说明

> 本章按大赛要求，如实说明本项目在使用 AI 工具时的范围、方式与人工核验过程。

### 8.1 使用原则

1. **AI 辅助而非替代**：AI 用于提升效率，产品规则、算法设计、数据校对与最终决策均由团队成员人工完成；
2. **可核验**：AI 生成内容（产品内回答、开发期代码/文档）均经过人工审查、测试或核对；
3. **不越权**：不将用户隐私数据（身份证号、密码等敏感字段）提供给 AI 工具。

### 8.2 产品内 AI 使用（DeepSeek 大模型）

| 场景 | 用途 | 人工核验/边界 |
|---|---|---|
| 学生能力画像解析 | 将结构化表单内容解析为十维得分与依据 | 输出经服务端校验、结构约束；结果标注"大模型解析" |
| 岗位能力画像解析 | 将招聘原文拆解为十维要求与技能/证书清单 | 原文未提及的维度标注"未提要求"；置信度随证据强弱变化 |
| AI 助手问答 | 基于知识库文章内容回答问题 | 回答可引用原文核对；用户可编辑/确认后存回知识库 |

### 8.3 开发过程 AI 使用

| 环节 | 使用方式 | 人工工作 |
|---|---|---|
| 编码 | AI 编程助手辅助生成部分页面逻辑、样式与接口封装 | 逐段审查、在微信开发者工具中实际运行验证、修复问题并回归 |
| 调试 | 辅助分析报错日志、定位组件兼容性问题 | 人工复现、验证修复、确认真机表现 |
| 文档 | 辅助撰写草稿与措辞 | 人工核对事实（功能是否存在、数据是否真实）、调整表述 |

### 8.4 声明

本项目产品内的 AI 能力仅用于画像解析与知识库问答，不用于自动投递、自动录用决策；AI 输出均经过规则校验与人工审查，匹配度、报告等结果仅作生涯规划参考，不构成录用承诺。
